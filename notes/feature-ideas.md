# Kankore Quest Tracker — 功能規劃比較研究

> 撰寫日期：2026-04-29（更新自前版）  
> 基於：`guide.html`（129 個任務、單一 HTML、PWA）+ wikiwiki.jp/kancollekai/任務 實際抓取分析

## 一、wiki 資料來源分析

**URL**：https://wikiwiki.jp/kancollekai/%E4%BB%BB%E5%8B%99

### 1-1 wiki 頁面結構

wiki 將任務分成 **7 個大類**，各自為獨立章節，另有月刊/年刊整理頁：

| 大類 | 說明 | 大約任務數 |
|------|------|-----------|
| 編成 | 艦隊編成相關 | 50+ |
| 出撃 | 戰鬥出撃相關 | 70+ |
| 演習 | 演習練度 | 15+ |
| 遠征 | 遠征派遣 | 20+ |
| 補給/入渠 | 補給與修理 | 4 |
| 工廠/改装/改修 | 建造、解體、裝備改修 | 若干 |
| マンスリーまとめ / イヤリーまとめ | 月刊/年刊任務整理 | — |

### 1-2 wiki 提供的資訊欄位

| 欄位 | 說明 |
|------|------|
| 任務名稱 | 任務標題（日文） |
| 任務內容 | 達成條件詳細說明 |
| 開放條件 | 前置任務文字（非結構化） |
| 燃料/弾薬/鋼材/ボーキ | **各別數字**（guide.html 沒有） |
| その他報酬 | 開発資材、高速修復材、戦略P、特定裝備/艦娘 |
| 備考 | マンスリー、イヤリー、特殊條件等 |
| 出撃海域 | 部分任務有標注（如「北方海域:第四海域」） |

**重要**：wiki 的任務分類（出撃/演習/遠征 等）是「任務種別」，跟 guide.html 的 `cat`（故事線）是完全不同的維度。

## 三、差距分析（Gap Analysis）

### ❌ wiki 有、guide.html 缺的資訊

| # | 缺失項目 | 現況 | wiki 的樣貌 | 影響 |
|---|---------|------|------------|------|
| G1 | **任務種別**（出撃/演習/遠征/工廠/改装/編成）| `cat` 只記故事線，不記任務種類 | 7 種類別，各自有章節 | 高 |
| G2 | **資源報酬數字**（燃/弾/鋼/ボーキ）| 全混在 `reward_text` 純文字 | 各別數字欄位 | 高 |
| G3 | **戦略P 數量** | 混在 `reward_text`，無結構 | 明確數字（如「戦略P:800」）| 中 |
| G4 | **recurrence 覆蓋率極低** | 129 個任務僅 7 個有標記 | wiki 有 マンスリーまとめ 整理 | 高 |
| G5 | **出撃海域結構化** | `info[]` 裡的非結構化文字 | 部分任務有標注（如「3-4」）| 中 |
| G6 | **reset 精確時間規則** | 無任何說明 | 遊戲固定 JST 05:00 reset | 中 |
| G7 | **編成要求結構化** | 散落在 `info[]` 文字中 | 文字說明（如「軽巡旗艦+駆逐2隻」）| 低 |
| G8 | **wiki 外部連結** | 無任何 wiki 入口 | 即為 wiki 本身 | 低 |
| G9 | **開発資材/改修資材數量** | 混在 `reward_text` | 分開列出 | 中 |

### ✅ guide.html 勝出的地方

| 優勢 | 說明 |
|------|------|
| **完整 DAG 依賴圖**（prev/next）| wiki 只有前置條件文字，guide 有機器可讀的邊關係 |
| **故事線分類**（Littorio/Z1）| wiki 不以故事線組織 |
| **即時進度追蹤**（localStorage checkbox）| wiki 無此功能 |
| **離線 PWA** | wiki 需要網路 |
| **自訂 info 備忘** | 可以自己補充攻略提示 |

## 四、功能 / UI / 設計建議

> **核心約束**：手機優先 · 單一 HTML 檔案 · 離線可用  
> 所有建議均在單一 HTML + 內聯 JS/CSS + localStorage 架構下完成，不引入打包工具或多檔框架。

---

### 類別 A：資料欄位補強（需要補資料，效益最大）

---

#### A1. 任務種別（`type` 欄位）+ 種類 badge

**建議**：為每個 task 加 `type` 欄位，值為以下之一：

```
"formation" | "sortie" | "exercise" | "expedition" | "supply" | "factory" | "remodel"
```

在任務卡片名稱前顯示對應 emoji badge：

```
🗂 [t010] はじめての「編成」！    ← formation
⚔️ [t011] 「北号作戦」を実施せよ！  ← sortie
🚢 [t008] 中部西海域潜水艦哨戒を実施せよ！ ← expedition
🏭 [t123] 新型「艦戦」の改良     ← factory
```

**為什麼有用**：
- 玩家今天只想做遠征任務時，一眼掃過去就能過濾，不需要讀完整段說明
- 是後續 C1（種類篩選 tab）和 B2（今日推薦任務）的前提欄位
- 手機碎片時間查閱效率大幅提升

**實作難度**：低（badge 渲染 < 1h；需人工補 102 筆 `type` 值，估計 2–3h）

**需要新資料**：是，建議對照 wiki 7 大分類手動補

---

#### A2. 資源報酬數字化（`res` 欄位）

**建議**：新增 `res` 欄位：

```json
"res": { "fuel": 100, "ammo": 100, "steel": 0, "baux": 0, "devmat": 2, "modmat": 0, "rp": 800 }
```

同時保留 `reward_text` 作為 fallback 顯示。

**為什麼有用**：
- 可視化每個任務的報酬（油桶🛢×100 / 砲彈💣×100 / 鋼鐵🔩×0 / 礦石⛏×0）
- 可做「今日最優資源刷取路線」計算（哪幾個任務加總鋼材最多）
- 可統計「完成所有未做任務共能獲得多少資材」
- 是 C1（報酬圖示）和 C3（路徑優化）的前提

**實作難度**：中（資料補充約 80 筆，可從 `reward_text` 用正則半自動抽取；UI 本身只需 1–2h）

**需要新資料**：是，建議寫個小腳本從 `reward_text` 抽取然後人工校對

---

#### A3. 補全 `recurrence` 欄位（目前只有 5% 覆蓋率）

**建議**：為所有 102 個任務補上週期：

```
"once" | "weekly" | "monthly" | "yearly"
```

目前 7 筆有標記，約有 20–30 筆月刊/年刊任務尚未標記。

**為什麼有用**：
- B1（reset 倒數計時）和 B2（今日推薦任務）完全依賴此欄位
- 可在卡片上顯示 🔁月 / 🔁年 標記，讓玩家知道「這個每月會 reset」
- 是最低成本、影響最大的資料補充項目

**實作難度**：極低（加欄位值 + 更新顯示標籤，資料查核約 1–2h）

**需要新資料**：是，需要確認哪些任務是月刊/年刊

---

#### A4. 出撃海域標記（`area` 欄位）

**建議**：sortie 類型任務加 `area: "3-4"` 格式欄位（`"-"` 格式）。

```json
{ "id": "t011", "type": "sortie", "area": "4-3" }
```

**為什麼有用**：
- 玩家在刷某張地圖時，可以一次查「這張地圖有哪些任務能順便做」
- 手機上「今天刷 3-4，同時做哪些任務」是高頻查詢
- 未來可加「海域任務清單」視圖

**實作難度**：低（加欄位 + 篩選邏輯約 2h；資料需從 wiki 查 10–20 筆）

**需要新資料**：是，部分任務

---

### 類別 B：時間與 Reset 工具（低難度、高回報）

---

#### B1. Reset 倒數計時器

**建議**：在 header 加一個常駐小區塊（可折疊），顯示距離各週期 reset 的倒數：

```
┌──────────────────────────────────────┐
│  月刊 reset  還剩  3天 14:22:05      │
│  年刊 reset  還剩  246 天            │
└──────────────────────────────────────┘
```

JST reset 時間規則（hardcode 即可）：
- **月刊**：每月 1 日 JST 05:00
- **週刊**：每週一 JST 05:00
- **年刊**：每年 1 月 1 日 JST 05:00

```js
// 計算下次月刊 reset（ms）
function nextMonthlyReset() {
  const now = new Date();
  const jst = new Date(now.getTime() + 9 * 3600000);
  // 下個月 1 日 05:00 JST = 前一天 20:00 UTC
  const next = new Date(Date.UTC(jst.getUTCFullYear(), jst.getUTCMonth() + 1, 1, -4, 0, 0));
  return next - now;
}
```

**為什麼有用**：
- 月末是最緊張的時間，玩家最需要知道「還剩幾小時」
- 完全不需要新資料，純 JS `Date` 計算
- 手機上特別有感，不用自己算日期

**實作難度**：低（< 1h，完全不依賴新資料）

**需要新資料**：不需要

---

#### B2. 今日推薦任務面板

**建議**：新增一個「TODAY」tab 或頂部折疊卡片，自動判斷並列出：

1. **本月尚未完成的月刊任務**（高優先）
2. **目前已解鎖、可直接完成的任務**（前置全完成）
3. **月末最後 3 天**：警示顯示「月刊 reset 即將來臨！還剩 X 小時」

排序邏輯：月刊未做 → 有高資源報酬 → 前置少的任務

**為什麼有用**：
- 手機碎片時間開 App，一眼看到「今天做這幾個」就夠了
- 不需要手動翻 100+ 任務找哪些能做
- 結合 A3（週期）+ A2（報酬）可以做更智慧的排序

**實作難度**：中（邏輯約 3–4h；依賴 A3 recurrence 資料完整性）

**需要新資料**：依賴 A3

---

#### B3. 一鍵 Reset 週期任務

**建議**：在月刊/年刊任務群旁加「月初 Reset」按鈕，批次將 `recurrence: monthly` 的任務設回未完成。同理提供年刊 reset 鈕。加一個確認 dialog 防誤觸。

**為什麼有用**：
- 目前月初要一個一個手動取消勾選，非常麻煩
- 是玩家每月最常見的痛點之一
- 實作極簡單，回報極高

**實作難度**：低（localStorage 操作 + dialog，< 30min）

**需要新資料**：依賴 A3 資料完整

### 類別 C：視覺化強化

---

#### C1. 任務種別篩選 Tab + badge

**建議**：現有橫向 tab 列（目前是故事線 tab）加入種別篩選層，或加一排種別 tab：

```
[全部] [出撃⚔️] [遠征🚢] [工廠🏭] [演習🎯] [編成🗂] [改装⚙️]
```

各任務卡片左側加對應 badge（依 `type` 欄位）。

**為什麼有用**：
- 今天要做遠征，直接點「遠征」只看遠征任務，不被出撃任務分心
- 是最直觀的手機過濾方式
- 現在的故事線分類（主線/D線/E線）+ 種別篩選 = 雙維度過濾，覆蓋大部分使用情境

**實作難度**：低（依賴 A1 的 `type` 欄位，UI 修改 < 2h）

**需要新資料**：依賴 A1

---

#### C2. 進度統計面板（各路線 + 全域）

**建議**：點擊 header 的進度計數（目前是「X/102」）展開一個統計卡片：

```
┌─────────────────────────────────────┐
│  總進度       ██████░░░░  62/102    │
│  主線/支線    ████████░░  38/75     │
│  D: Littorio  ███░░░░░░░   8/27     │
│  E: Z1        █████░░░░░  10/21     │
├─────────────────────────────────────┤
│  一次性       ████████░░  55/72     │
│  月刊         ██░░░░░░░░   2/20     │
│  年刊          ░░░░░░░░░░   0/5      │
└─────────────────────────────────────┘
```

**為什麼有用**：
- 知道哪條故事線快完成，可以集中衝刺
- 看到「月刊只做了 2/20」馬上有危機感
- 幾乎不需要新資料，主要是 UI 工作

**實作難度**：低（UI 約 1–2h；月刊/年刊分組依賴 A3）

**需要新資料**：月刊/年刊分類依賴 A3

---

#### C3. 任務卡片報酬 mini-badge

**建議**：在任務卡片 meta 行（標籤那排）加一行報酬 icon：

```
⚔️ 出撃  🔁月  │  🛢×100  💣×100  🔧×2  P×800
```

不需要展開就能掃視報酬，月末快速判斷「這個值得做嗎」。

**為什麼有用**：
- 現在報酬藏在 `reward_text` 展開面板裡，掃描成本高
- 資源報酬 icon 是最常查的資訊，放卡片外層效率最高

**實作難度**：低（UI 約 1h；完全依賴 A2 資料）

**需要新資料**：依賴 A2

---

#### C4. DAG 局部視覺化（聚焦模式）

**建議**：點擊任務展開面板裡的「查看依賴圖」按鈕，彈出一個 modal，顯示：
- 該任務的**前兩層 prev 節點**（前置鏈）
- 該任務的**後兩層 next 節點**（解鎖鏈）
- 已完成節點綠色、可做節點藍色、鎖定節點灰色

用 SVG 繪製，最多 15–20 個節點，不需要完整 DAG 佈局。

**為什麼有用**：
- 「這個任務完成後會解鎖什麼？」是高頻問題
- 局部圖比完整 DAG 實作難度低很多
- 讓玩家規劃 2–3 步的策略，不需要全圖

**實作難度**：中（SVG 繪製 + 局部 BFS，約 5–8h；比完整 DAG 易得多）

**需要新資料**：不需要（prev/next 已完備）

### 類別 D：實用工具

---

#### D1. 最短前置路徑計算

**建議**：加「規劃路線」功能，使用者選定目標任務（或直接從任務展開面板觸發），系統在 DAG 上 BFS 算出**從目前完成狀態出發的最短前置鏈**，按順序列出「需要先做這 N 件事」。

範例輸出：
```
目標：t123 新型「艦戦」の改良（烈風改）
尚需完成（3步）：
  1. t061 機種転換（村田） ← 可以做！
  2. t117 南方海域珊瑚諸島沖の制空権を握れ！ ← 等 1
  3. t123 新型「艦戦」の改良 ← 等 2
```

**為什麼有用**：
- D 路線有十幾個前置任務，玩家不知道從哪邊開始
- 省去手動追 prev 鏈的時間
- 手機上尤其有用，不需要開 wiki 對照

**實作難度**：中（BFS on DAG 邏輯約 2–3h；UI 設計另需 1–2h）

**需要新資料**：不需要

---

#### D2. 報酬反向搜尋

**建議**：搜尋框改為支援報酬名稱搜尋，例如搜「烈風」會顯示所有 `rewards[]` 或 `reward_text` 包含「烈風」的任務。

**為什麼有用**：
- 目前搜尋只按任務名稱，但玩家更常問「要拿到 X 裝備需要做什麼任務」
- 反向查詢比正向查詢在實際使用中更常見
- 現有 `rewards` 欄位已有 15 筆，搜尋 `reward_text` 也能湊合

**實作難度**：極低（修改搜尋邏輯 < 30min）

**需要新資料**：A2 補完後效果更好，但現有資料就能用

---

#### D3. wiki 連結快速入口

**建議**：每個任務展開面板底部加「📖 wiki 查詳情」連結，跳至 `https://wikiwiki.jp/kancollekai/任務`（帶任務名稱作為搜尋詞或錨點）。

**為什麼有用**：
- 看到不懂的任務，一鍵開 wiki，不需要手動複製搜尋
- 零成本實作，30 分鐘搞定
- 離線時連結不可用，但有網路時非常實用

**實作難度**：極低（< 30min）

**需要新資料**：不需要

#### D4. 艦娘所需清單（我缺哪艘艦？）

### 類別 E：手機體驗優化

---

#### E1. 折疊已完成任務群

**建議**：DONE 群組標題旁加折疊/展開按鈕，預設折疊。已完成任務多了之後（尤其主線完成 70% 以上），DONE 群組佔據大量螢幕空間。

**為什麼有用**：
- 手機螢幕小，DONE 清單展開很長，要一直滑才能看到 AVAILABLE
- 預設折疊讓畫面直接聚焦在「能做的任務」
- 玩家還是可以點開 DONE 確認完成狀態

**實作難度**：低（CSS display 切換 + localStorage 記憶狀態，約 1h）

**需要新資料**：不需要

---

#### E2. 前置任務 badge 可點擊跳轉

**建議**：任務卡片上的前置任務 tag（prereq badge，`upcoming` 狀態已顯示）改為可點擊，點擊後直接捲動到該前置任務並高亮。

**為什麼有用**：
- 現在看到「需要先完成 t030」，要自己翻找那個任務在哪裡
- 可點擊跳轉省去搜尋步驟，手機上尤其有感

**實作難度**：低（scroll + highlight 動畫，約 1h）

**需要新資料**：不需要

---

#### E3. 每任務個人筆記（per-task note）

**建議**：任務展開面板加一個可編輯的 textarea「我的筆記」，內容存到 `localStorage` key `note_${id}`。用來記錄個人攻略心得（如「丁難度 B 勝利可」「要記得帶輪型陣」）。

**為什麼有用**：
- 月刊任務每月 reset 後重做，上次踩的坑下次不用再查 wiki
- 完全離線、不需要後端
- 實作極簡，現有 textarea 樣式可直接複用

**實作難度**：極低（< 30min）

**需要新資料**：不需要

---

#### E4. 滑動手勢完成任務（Swipe）

**建議**：任務卡片支援 swipe-right 標記完成，swipe-left 展開詳情（iOS Reminders 風格）。

**為什麼有用**：
- 手機上 checkbox 觸控面積小，容易誤點
- Swipe 是手機任務 App 的標準 UX pattern
- 單手操作更流暢

**實作難度**：中（`touchstart/touchmove/touchend` 事件 + CSS transition，約 3–4h）

**需要新資料**：不需要

---

#### E5. 震動回饋（Haptic）

**建議**：完成任務勾選時呼叫 `navigator.vibrate(50)`（50ms 短震動）。

**為什麼有用**：
- 提升完成任務的成就感，有明確的觸覺確認
- 防止誤點（震動 = 已觸發，玩家能感知）

**實作難度**：極低（1 行 code，10min）

**需要新資料**：不需要

## 七、單一 HTML 實作備忘

所有功能可在「單一 HTML + 內聯 JS/CSS + localStorage」架構下完成：

```
倒數計時    → setInterval + Date（JST = UTC+9）
DAG 視覺化  → 原生 SVG，無需外部 lib（局部圖 < 20 節點可行）
進度條      → CSS width: calc(X * 1%)
Swipe       → touchstart/touchmove/touchend 原生事件
Export      → navigator.clipboard.writeText() 或 <a download>
震動        → navigator.vibrate(50)
```

新增 localStorage keys 建議：

| Key | 用途 |
|-----|------|
| `kc_quest_state_v2` | 現有完成狀態（繼續用）|

| `kc_prefs_v1` | 使用者偏好設定（折疊狀態、難易度等）|
| `kc_ships_v1` | 艦娘收藏標記（D4 功能用）|
